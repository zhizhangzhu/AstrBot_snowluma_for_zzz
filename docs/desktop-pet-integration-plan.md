# AstrBot × Coopanion 桌宠接入计划书

- 整理日期：2026-10-30，北京时间。
- 文档用途：记录方案约定，作为后续设计、开发、发布和需求验收的核对依据。
- 当前阶段：用户已授权按计划开发。首版源码及隔离测试进度见[实现与验收](desktop-pet-implementation.md)；生产部署、推送和安装包发布仍分别安排。
- 本文中的“应”“必须”表示需求，不表示功能已经实现。实际完成状态以实现记录和对应验收证据为准。
- “已确认”来自本次讨论中的明确选择；“建议默认”是讨论中提出并沿用的设计建议；“待验证”需要在实现前检查实际条件。

## 1. 目标与方案选择

### 1.1 已确认的目标

为现有 AstrBot Bot 增加 Windows 桌宠终端。小小情通过同一套人格、记忆、近期上下文和主动决策，在 QQ 与桌宠上持续交流，并感知和使用桌宠提供的互动、动作与兼容扩展能力。

桌宠客户端与 Linux 上的 AstrBot/SnowLuma 保持为独立应用。桌宠关闭不影响服务器持续运行、QQ 收发以及不依赖桌宠的后台活动。

### 1.2 已确认的选择

| 项目 | 约定 |
| --- | --- |
| 应用部署 | Windows 运行桌宠；Linux 持续运行 AstrBot、SnowLuma 和 QQ |
| 交互模式 | 桌宠作为新的平台终端，共享人格和记忆，分别收发消息 |
| QQ 镜像 | 不要求把桌宠和 QQ 的每条消息都重新发送到另一端 |
| 通信 | Windows 主动建立 WSS 双向长连接；连接建立后 Linux 可主动推送 |
| SSH 隧道 | 不作为本项目的业务通信实现 |
| 模型与主动决策 | 统一放在 AstrBot；复用其现有模型配置 |
| 客户端职责 | 感知、呈现、执行、扩展运行与结果反馈 |
| 形象 | 第一版复用现有形象包；以后可开发专属形象包 |
| 客户端平台 | 第一阶段仅考虑 Windows |
| 版本管理 | 父仓库管理服务端和配套版本；Coopanion 作为子模块保留独立历史 |

“共享记录”和“再次发送”是不同操作。桌宠可以按需展示共同私聊记录，但展示历史不能再次触发 Bot 回复、发送 QQ 消息或重复写入记忆。

## 2. 部署与职责

```text
Windows 桌宠客户端
  ├─ 现有形象包、气泡、动作与本地动画
  ├─ 用户输入、触摸、状态感知
  ├─ Coopanion / Cortico 扩展运行环境
  └─ WSS 连接、消息确认和执行回执
                ↕
Linux：AstrBot 桌宠接入插件
  ├─ 配对认证、终端状态、协议与能力清单
  ├─ 桌宠消息和事件接入、工具远程调用
  └─ 与人格、记忆、陪伴及主动路由对接
                ↕
AstrBot 统一决策
  ├─ 人格、模型、共同上下文和记忆
  ├─ 用户档案、主动交流、自主生活与日程
  └─ 实际经历、日记与工具执行结果
                ↕
各 Bot 独立的 SnowLuma / QQ / QQ 空间
```

### 2.1 服务端

- 新增独立的 AstrBot 桌宠接入插件；最终名称和对外地址在设计时确定。
- 桌宠输入进入 AstrBot 的完整聊天处理流程，参与人格注入、用户识别、上下文、记忆捕获、工具调用和回复记录。
- 不采用绕过现有处理流程、只直接调用模型的简化聊天接口。
- 可以采用平台适配器，或提供具有等效完整行为的插件入口；需要先核查 AstrBot 当前版本的接口。
- 与陪伴、记忆插件建立明确的服务接口。独立插件并不意味着仅增加一个插件文件即可完成所有对接。
- 现有 QQ 工具继续通过正确 Bot 账号执行。桌宠来源不能造成 QQ 账号、主要用户或空间会话选择错误。
- QQ 专用逻辑需要显式适配；不能通过伪装消息来源、借用其他用户会话或绕过人格隔离来获得兼容。

### 2.2 Windows 客户端

- 保留形象、互动、语音输入基础及扩展加载、配置与生命周期管理能力。
- 负责执行服务端选择的动作和工具，报告真实状态与结果。
- 保留必要的本地物理行为、动画和日常走动；这些行为无需逐次请求模型。
- 连接模式下不再独立运行一套与 AstrBot 并行的人格、长期记忆和主动模型决策。
- 断线后可保留本地动画和明确的连接状态提示，不能冒充小小情生成新的对话或声称远端操作成功。
- 不向客户端复制 AstrBot 的 OAuth 刷新凭据、QQ 登录态、完整记忆数据库或模型密钥。

## 3. WSS、证书与配对

### 3.1 网络约定

- 仅实现 WSS 业务连接。无须 Linux 另行连接 Windows，也无须 Windows 开放入站服务端口。
- Windows 建立连接后，双方通过同一连接发送消息、事件、指令和回执。
- 目前只有服务器 IP，不以购买域名为前提。
- 已知管理入口使用内网地址 `10.74.4.16`。能 SSH 访问不代表桌宠接口端口一定可达，需要另行核验路由、防火墙与端口。
- 不将现有 AstrBot 管理面板直接作为未经限制的公网桌宠接口。
- WSS 的监听端口、TLS 终止方式、Compose 接入方式和绑定地址均待验证与确定；本文不指定尚未建立的可用接口。

### 3.2 证书信任

- WSS 必须使用 TLS 证书。使用为当前服务生成的专用证书或私有 CA，不要求购买公开证书。
- 证书应正确覆盖实际连接的 IP；客户端校验服务器身份与证书有效性。
- 首次配对通过已有可信渠道核验服务器的信任信息，不能仅从尚未验证的连接获取并盲目信任。
- 信任范围限定在桌宠与指定服务器之间，不要求修改整个 Windows 的系统根证书配置。
- 不通过关闭证书校验、忽略所有 TLS 错误等方式实现连接。
- 正常证书续期尽量不要求重新配对；信任根或服务器身份发生变化时，应重新核验。证书轮换、撤销与 IP 变更流程需在实现时一并设计。
- 私有 CA、证书或公钥的具体固定方式，以及证书有效期和续期机制，是待验证的技术选型，尚未固定。

### 3.3 配对与身份认证

- 配对同时解决服务器身份确认和客户端身份确认，二者不能互相替代。
- 建议提供一次配对流程，将服务器地址、必要的公开信任信息和配对凭据一并导入客户端。
- 配对文件不得包含服务器私钥、CA 私钥、模型 OAuth 凭据或 QQ Cookie。
- 每个设备使用独立、可撤销的身份凭据；初始化凭据的有效期和交换流程在设计时确定。
- 客户端长期凭据使用 Windows 适当的受保护存储方式，具体实现待选。
- 配对文件、证书私钥、设备凭据与本地状态不进入源码仓库或通用安装包。

### 4.2 绑定规则

- 一个桌宠客户端同时连接一个 AstrBot 服务，并明确绑定其中一个人格和一个已验证用户身份。
- 一个 AstrBot 服务可以管理多个人格；“绑定一个服务”不等于自动拥有该服务所有人格的访问权限。
- 第一版以小小情与其主要用户为主要接入对象，同时核验初小晴既有链路不受影响。
- 后续为初小晴接入时使用独立配对与隔离域，不能继承小小情的用户身份、记忆、会话或空间凭据。
- 桌宠用户与 QQ 用户的共同身份由可信配对关系建立，不能由客户端自行填写一个 QQ 号就取得该用户的记忆。
- 人格、Bot 账号、用户、设备、终端与会话均需保留归属；这些标识的协议字段名称尚未固定。
- 切换服务器、人格或用户绑定后，旧连接、能力清单和未完成指令需要失效或按明确规则收尾。
- 建议默认只有一个主要互动终端；多设备同时连接时的排他或主设备选择规则需要明确，避免同时弹出主动消息。

## 5. 共同上下文与记忆

### 5.1 共享范围

- 同一人格与同一已绑定用户共享近期私聊上下文、长期记忆、用户档案与重要互动经历。
- QQ 聊过的内容可以在桌宠继续，桌宠发生的交流也可以在 QQ 继续。
- 不只复制人格提示词；新平台必须参与记忆写入、检索、更新和来源追溯。
- 同一句称呼、偏好或关系信息只更新共同用户档案，避免在两个平台各维护一份互相矛盾的画像。
- 群聊、其他用户与其他人格继续遵循既有可见范围，不能因为新增桌宠就汇总暴露全部消息。
- 客户端展示共同记录的范围只限其绑定用户有权访问的记录。

### 5.2 来源与互动语义

每条记录至少应能追溯下列事实；字段形状是设计要求，不是已经固定的协议：

| 信息 | 用途 |
| --- | --- |
| 事件或消息标识、发生时间 | 排序、关联、去重和追溯 |
| 人格、Bot 与用户归属 | 隔离与共同身份识别 |
| 来源终端 | 区分 QQ、桌宠等输入来源 |
| 扩展来源 | 标记桌宠中的具体 World 或能力 |
| 发起方、接收方或动作目标 | 区分自己做的事和用户做的事 |
| 互动类型 | 区分文字、摸头、拖动、QQ 戳一戳等 |
| 原生消息标识与关联关系 | 追踪引用、回复、确认和工具回执 |
| 执行状态与证据 | 区分意图、请求、成功、失败、中断和未知 |

语义示例：

- QQ：用户向小小情发送“晚上好”。
- QQ：小小情向用户发起戳一戳，平台已确认。
- 桌宠：用户摸小小情的头。
- 桌宠：小小情尝试走到鼠标旁，因用户拖动而被打断。

来源标签用于帮助模型理解，不要求模型每次在自然回复中朗读标签。桌宠摸头不能被记录为 QQ 戳一戳，桌宠事件也不能伪造成可引用的 QQ 原生消息。

### 5.3 真实输出记录

- 通过气泡、提问选项、工具旁路等方式发送的有效话语，同样进入共同上下文。
- 小小情应能知道自己实际说过、问过什么，以及用户回答了哪个问题。
- 文本由 LLM 按绑定人格与当前上下文生成，不采用固定角色台词作为常规回复或失败兜底。
- 连接错误、加载状态等产品界面提示可以使用明确的固定状态文案，与角色台词区分。
- 客户端自己的显示记录不能重复触发 Bot；同一事实也不能因 QQ 与桌宠的记录同步而被重复学习。
- 高频动画、心跳与重复状态只保留必要运行信息，不逐条转成长期记忆。

## 6. 消息路由与打扰规则

### 6.1 被动回复

- 从 QQ 收到的正常消息在 QQ 回复；从桌宠收到的消息在桌宠回复。
- 生成回复时保留输入来源与回复目标；桌宠中途上线不能擅自改变已在处理的 QQ 回复目标。
- 不因为桌宠在线就停止正常处理用户主动发来的 QQ 消息。
- 不要求将桌宠私聊再次发送到 QQ，也不默认将其他 QQ 联系人或群聊转发到桌宠。

### 6.2 主动交流

- 桌宠正常可用、允许交流时，对绑定用户的主动交流优先通过桌宠发送。
- 此时暂停对同一用户的普通主动 QQ 消息和主动戳一戳，避免两端同时打扰。
- 这项优先级只作用于相应人格和用户，不全局关闭另一个人格或其他用户的功能。
- 桌宠不可用后，后续主动交流按原有权限、时段、频率与配额规则切回 QQ。
- 开启免打扰后不能通过换到 QQ 绕过；两端共同遵循适用的打扰约束。
- 不依赖桌宠的资料阅读、新闻、QQ 空间浏览等后台活动继续运行。
- QQ 空间仍使用各 Bot 自己的 SnowLuma 原生后台接口，不依赖桌宠或浏览器打开。

### 6.3 可用状态

- 分别报告网络连接、客户端就绪、形象可用、窗口显示、锁屏/休眠、用户空闲和免打扰等状态。
- 网络连接存在，不等于气泡一定可见或用户一定适合被打扰。
- 锁屏、休眠时不把桌宠视为正常的主动交流目标；具体仍可后台执行的工具由其能力状态单独报告。
- 手动隐藏、全屏应用、长期无交互等情况下如何处理非紧急消息，采用明确可配置规则；不能简单把所有情况一律当作断线。
- 建议隐藏或免打扰时优先等待，而不是立即绕到 QQ 联系。确切默认策略需在交互设计中核对。

## 7. 并发、重连与投递可靠性

### 7.1 共同对话协调

- 同一人格与用户的两端输入统一排序，避免 QQ 和桌宠各自维护会话分叉。
- 新消息可以补充尚未完成的回答，或按支持的中断机制停止旧任务。
- 已经实际输出的内容保留；不能因重新生成而从真实经历中抹去。
- 对话状态、记忆更新与工具操作需要合理协调，避免同时生成互相矛盾的回复。
- 不以一把长时间占用的全局锁阻塞所有人格、所有用户或独立工具任务。

### 7.2 确认与去重

- 消息、事件和动作携带可关联的唯一标识；重连和重传沿用原标识。
- 区分“进入发送队列”“远端收到”“已经显示”“动作完成”等状态；不把套接字发送成功等同于用户已读或动作成功。
- 客户端保留必要的去重信息和回执状态，服务端在重连后可以核对。
- 相同文字的两次真实发言不能被误认为同一条重传，不能仅按内容去重。
- 跨网络不能凭缺失回执断言成功或失败；结果未知时先核对，避免立即在 QQ 或桌宠重复执行。

### 7.3 断线与恢复

- 轻量心跳和自动重连不调用模型；具体间隔与退避参数在实现时配置。
- 断线时及时更新可用能力，收尾正在执行的任务，不无限期占用对话处理资源。
- 重连后核验同一设备与绑定、同步必要状态和近期上下文，再恢复有效任务。
- 已显示消息不重复播放；过期的招呼、挥手等短时指令丢弃。
- 创作等可继续活动与小游戏等需等待活动分别处理，不把所有待办一次性补做。
- 有外部影响且结果未知的操作不能盲目重试；取消只表示请求停止，不能据此声称外部影响已经撤销。
- 在回复或动作处理中遇到插件热重载、客户端更新、服务重启，同样保留去重与结果核对语义。

## 8. 身体、互动与媒体

### 8.1 形象与动作

- 第一版复用已提供的形象包，不以制作新形象为开工前提。
- 具体采用哪个包、产品名称和图标尚未最终指定。
- 将当前形象实际支持的表情、动作、移动目标与限制告诉小小情。
- 小小情按人格、兴趣和当前情境选择说话或行动，也允许不行动。
- 客户端报告动作完成、失败、被打断和不可用等结果，不用固定动画推断实际执行。
- 形象更换、加载失败或动作词表变化后刷新能力，不能继续调用不存在的动作。

### 8.2 感知范围

- 触摸、拖动、气泡回答等直接互动作为第一版基础能力。
- 文字聊天为第一版重点；语音输入可以复用现有本地转写能力，具体交付顺序待验证。
- 前台应用信息、屏幕截图和电脑操作分别设置，后续逐项开放，不以接入桌宠为由默认全部开启。
- 沿用客户端的实际权限、操作限制与用户接管行为；QQ 或外部内容不能自行扩大 Windows 操作权限。
- 感知范围以实际启用、可用的功能为准，不声称能读取客户端未提供的信息。

### 8.3 媒体

- 协议预留图片、文件、语音转写和工具附件传输，关联到对应消息与工具调用。
- Windows 本地路径不能当作 Linux 已可读取的文件；需要传输内容或提供受控访问方式。
- 图片或画布结果不仅记录“生成成功”，还应让模型和用户能在所需终端访问实际结果。
- GIF 保留单个动态媒体的语义与必要时间信息，不能误当成用户发送的多张独立图片。
- 文件大小、分块、缓存、保留时长和清理机制待设计，不把大量媒体重复写入上下文。

## 9. Coopanion 扩展通用接入

### 9.1 已确认的方向

- 保留扩展市场及扩展运行环境，开发通用 World 桥接层。
- 不要求每安装一个标准扩展，就重新开发一个对应 AstrBot 插件。
- 扩展继续在 Windows 执行；AstrBot 通过 WSS 接收环境说明、能力与事件，远程调用工具并取得回执。
- 不能只把客户端裁剪成一个显示气泡的界面，而丢失其扩展运行基础。

### 9.2 通用桥的覆盖面

- 发现已加载扩展及其版本、环境说明、工具参数与实时可用状态。
- 转发事件、文本、附件和必要状态；保留扩展来源与事实边界。
- 调用工具并返回成功、失败、中断和未知结果。
- 扩展启用、停用、卸载、配置变化或连接变化后更新能力清单。
- 工具调用绑定具体设备、扩展和能力版本，避免清单变化后误调用同名旧工具。
- 把外部环境内容作为观察资料处理，不让它自行替换人格、系统规则或设备授权。

### 9.3 兼容范围与限制

| 类型 | 计划 |
| --- | --- |
| 标准工具、环境说明型 World | 优先通过通用桥接入 |
| 会推送变化的 World | 接入事件及其触发、合批、上下文语义 |
| 依赖打断、事件选择和交接的复杂 World | 补齐所需宿主能力并逐类验证 |
| 依赖流式演出、实时游戏或后台推理的 World | 核验流式输出、取消与后台计算接口，必要时专项适配 |
| 模型供应商或替换 Bot/Persona 的扩展 | 不作为普通外部能力自动接入或替换小小情 |

- 官方兼容等级从工具、事件流、投递语义到实时能力逐步增加；不能只转发工具名，就宣称所有扩展完整兼容。
- 显示“已发现、可用、部分支持、暂不支持”等状态及原因；不可用能力不伪装成可以成功执行。
- 新扩展完成安装并成功加载后才能更新实际能力，不能只依据市场描述判断已经可用。
- 能力自动发现与主动执行资格分开表达。已启用、兼容、可用且已允许的能力进入主动候选；沿用功能本身已有的权限，不额外强制每个普通扩展都单独改代码或批准一次。
- “可以主动调用”不等于必须频繁调用，使用时机由小小情决定。
- 需要模型推理的扩展原则上接入 AstrBot 统一模型能力，记录用途与结果；无法桥接的情况明确报告，不自动配置另一套模型账户。

### 9.4 开发边界

- 遵守 Coopanion 的 AGENTS.md，开发前阅读锁定 Cortico 的 PHILOSOPHY.md。
- 不原地修改 vendor/cortico；若确实需要框架新增接口，遵循其上游贡献与依赖更新流程。
- 优先在客户端的连接模式、扩展宿主桥和服务端插件之间建立清晰接口。
- 具体实现能复用多少现有宿主能力仍需技术验证；当前没有承诺所有市场扩展无需适配。

## 10. 主动性与自主生活日程

### 10.1 统一决策

- 主动交流、自主活动选择、模型调用、人格与长期记忆统一由 AstrBot 协调。
- 不让 Windows 和 Linux 分别维护两套主动模型循环、主动联系队列和生活日程。
- 客户端可维护必要的本地定时器、工具运行状态及机械行为，它们通过事件和回执报告给 AstrBot。

### 10.2 让小小情理解能力的主动用途

- 工具说明之外，还需提供使用情境、当前环境、是否需要用户参与、后台执行条件与限制。
- 已可用桌宠能力进入活动候选；小小情可以按人格、兴趣、近期交流和当天目标主动选择。
- 她应知道自己有桌宠终端、当前身体形象和扩展能力，也知道断线后哪些能力已失去。
- 不把“调用工具”限制为只响应用户明确命令。

### 10.3 全日计划与动态调整

- 保留已确认的“每天生成全天计划＋动态调整”，不因桌宠偶尔离线而放弃全天规划。
- 每日固定生成时间沿用配置，实现前核对当前设置；本计划书不新增未经确认的固定时刻。
- 计划注明活动目标、所需终端与能力、适宜时间、是否需要用户参与，以及延后、替代、恢复或过期策略。
- 桌宠可用时可安排画画、小游戏、互动等兼容活动；不可用时选择服务器可做的活动，或合理延后。
- 不能把尚未发生的桌宠经历编成日记，也不能将“改为查资料”写成已经完成原定创作。

| 目标 | 桌宠可用 | 桌宠不可用 |
| --- | --- | --- |
| 创作一张小画 | 调用兼容画板并记录实际产物 | 延后或准备相关资料，保持目标未完成 |
| 分享今天的发现 | 优先在桌宠交流 | 按主动规则选择 QQ 或等待 |
| 体验桌面小游戏 | 条件满足时启动活动 | 保留适宜待办，不虚构游玩 |
| 阅读新闻、浏览 QQ 空间 | 在服务器正常执行 | 在服务器正常执行 |

### 10.4 动态调整触发

- 桌宠上线、断线、休眠或可交互状态变化。
- 扩展成功加载、停用或工具可用性变化。
- 用户交流、提出新需求或开启免打扰。
- 活动完成、失败、被打断或到达计划执行时间。
- 程序先更新状态，再按实际影响触发必要的局部规划；短暂抖动合并处理。
- 不每秒或每分钟请求模型重算全天计划，不因每次鼠标移动而规划。
- 连接恢复后重新判断活动是否仍值得执行，不无条件补做全部积压任务。

### 10.5 计划、执行与经历

| 层次 | 含义 | 示例 |
| --- | --- | --- |
| 计划 | 希望完成，尚未发生 | 今天想画一张小画 |
| 执行 | 已发起、正在进行或等待反馈 | 画板工具已开始，尚未返回产物 |
| 实际经历 | 有可核验结果 | 图片已生成，或创作因断线中断 |

- 回执缺失时记录结果未知，不直接推定完成。
- 只有实际发生的内容进入已完成经历；失败和中断也可以成为真实经历。
- 日记与记忆能够引用互动对象、来源、实际内容和产物，避免只剩“与人聊过天”的空泛记录。
- 低价值心跳、在线状态刷新和重复回执保留必要审计，不挤占长期回忆。

## 11. 资源与故障控制

- 网络心跳、重连、动作播放、移动物理和高频状态由程序处理，不逐项调用 LLM。
- 模型主要用于交流、语义决策、活动规划和有意义的观察理解。
- 能力清单和环境说明按变化更新，避免每次对话无差别注入所有长说明。
- 主动活动遵循已有免打扰、频率、配额与用户权限；工具本身的成本和执行时长可参与选择。
- 扩展故障、客户端断线或不兼容不能拖垮正常 QQ 回复和其他人格。
- 工具任务需要可控超时与取消语义，不能无限期占用会话锁。
- 状态与诊断应能区分连接、认证、能力、模型、工具执行和投递问题，不只显示“插件加载成功”。
- 诊断不输出密码、配对凭据、QQ 登录态或无关用户的聊天内容。
