# 桌宠电脑操作：设置发现与授权验收

对应 `Coopanion/core/astrbot/native.ts`、`plugins/astrbot_plugin_desktop_pet/main.py`。北京时间 2026-11-03。

## 核对结果

用户 Windows 的正式小小情实例原配置为 `cua.enabled=false`、`control=true`、`permission=ask-once`、授权期限 30 分钟。关闭电脑操作时不发布键鼠工具，因此不会仅因客户端在线而申请控制。

AstrBot 原生装配漏传 `openCuaSettings`，导致原 World 的 `pet_cua_open_settings` 也不出现在关闭状态的能力目录。0.3.4 接回原习惯页的 `#/pet?cua=enable`；Bot 可在用户同意打开设置后引导启用，不能通过这个工具直接打开电脑控制。

模型所读的 World 环境和工具参数仍有“图片只显示在聊天页”的旧说明。现已与实际身体气泡 PNG/GIF 展示行为统一；图片原件和展示回执机制保持不变。

服务端 0.2.5 明确经过配对鉴权的桌宠输入来源，与共用 QQ 会话身份分别描述。原生工具调用可以触发客户端授权询问；拒绝、取消、锁屏、休眠和离线仍有效。明确未提交的工具请求返回 unavailable / submitted=false，不再误报结果未知。能力分页附当前锁屏状态、总工具数和下一页位置，避免遗漏后页的键鼠工具。

## 本机检查边界

- 正式客户端 0.3.3 已正常重启，临时调试端口关闭；原加密配对一致，重新连接小小情，称呼为猪猪。
- 一度启动独立“键鼠验收”实例以检查开关；用户要求使用正式实例后，该白色测试形象与临时服务已关闭、临时设备已撤销。
- 在正式桌宠聊天入口提交了标明“由维护操作提交”的验收请求，只允许一次 Shift 和鼠标回到同一位置，禁止文字输入、点击、滚动和截屏。
- 本轮临时改为每轮询问并禁用操作后截屏；随后完整恢复原 CUA 配置。第一轮未发生键鼠工具调用，客户端同时报告 locked=true，不能据此声称授权或键鼠执行成功。
- 用户随后确认当时确实锁屏，已解锁；客户端 locked 状态恢复为 false，排除这轮锁屏误判。第二轮由小小情在正式客户端实际调用 pet_cua_key（shift，screenshot=false），12:15:19 收到 completed；12:15:32 对同一鼠标坐标的 pet_cua_move（screenshot=false）也为 completed。每轮询问配置下，原生授权完成后才执行；没有代点允许、输入文字、点击、滚动或截屏。

## 回归

原生运行时回归经过真实 World 和桥接器：关闭状态发现设置工具、仍不提供按键工具，调用后打开原习惯页的启用位置。客户端 515 项及 World 204 项通过、3 项跳过，三项类型检查及运行时构建通过。

服务端最终本地桌宠与认知检查 67 项通过、3 项因本地缺少框架跳过；实际 AstrBot 镜像中 35 项通过，包含跨重载普通聊天、两个 Bot 作用域、真实工具调度和未提交回执。0.2.4 源码回退点保存在忽略目录 `backups/desktop-cua-20261103/server/`，没有修改两个 QQ 实例或其登录态。

## 可见演示与气泡尺寸

用户希望看到动作，因此另发起仅 Shift 一次、鼠标小幅移开后复位的演示。该轮原生授权 60 秒未获确认，pet_cua_key 返回 failed / not run；只统计注入 Shift 的本地测试窗计数为 down=0、up=0，鼠标位移为 0，验证没有越过授权。测试窗自动关闭；配置再次恢复。可见演示不算已执行。

用户截图确认真实表情图进入了身体气泡，同时发现顶部空白。纯图片仍创建 `.b-text`，其 `min-height:1.55em` 预留了一行。0.3.5 仅在有正文时创建文字区；PNG、GIF 和带正文图片的真实页面回归通过。客户端 518 项及 World 204 项通过、3 项跳过，三项类型检查与运行时构建通过。Windows 安装包验证新增纯图片回执；安装结果另见验收清单。

用户准备好后，可见演示在正式 0.3.4 客户端完成 Shift 和约 40 像素的鼠标移动：只统计注入 Shift 的测试窗确认 down=1、up=1。Bot 没有调用返回坐标的第二次 move，却口头报告已复位；维护操作随后恢复原坐标。记录中分别标明“Bot 已移动”和“维护已复位”，不把整段归为 Bot 全部完成。服务端补充多步任务逐项核对完成回执的说明；这是语义约束，不承诺能消除模型所有错误报告。测试窗关闭，CUA 配置已再次恢复原值。

用户随后授权离开电脑期间自动处理本轮限定验收的确认。原生键鼠正向验证已完成，不因此开启长期免确认权限；锁屏和休眠仍阻止真实输入。后续以安装和媒体展示检查为主。

隔离 Linux Electron 的实际渲染也已核对：同一 2px PNG，带正文气泡为 48px 高，纯图为 26px，纯图没有空正文节点，多出的 22px 行高已消除。该结果不替代 Windows 安装验收；首轮新增纯图验收失败，尚未安装 0.3.5，已补充失败回执与构建产物保存以定位。

Windows 失败回执已确认：第一条 reply 为 completed，紧接的 image-only-reply 返回 failed / expired_or_unavailable。客户端原来先发完成结果，再发布变化后的能力目录，紧接着的调用可能携带旧版本而被拒绝。新增连续调用回归先复现失败，再验证修复；现在能力更新先于完成回执发布，并等待已进行中的目录更新。最终客户端检查 520 项、World 204 项通过，3 项跳过，三项类型检查及构建通过。[最终 Windows 安装验收](https://github.com/zhizhangzhu/Coopanion/actions/runs/41580687347)通过，包含连续回复后的纯图片展示；只将这一通过验收的候选用于用户电脑升级。

临时维护的到期清理也修复了关闭顺序：先停止两个监听并关闭活跃对端，再等待服务器结束，避免等待尚未主动关闭的旧连接。真实 Unix 连接的到期退出回归通过；状态及命令入口也会检查期限。

用户电脑升级的首轮检查仍读到 0.3.4，因此没有按安装进程结束就报告成功。维护脚本的路径匹配改为规范化安装目录，且确认旧实例退出后再启动安装；Windows 曾短暂保留已请求退出的进程记录，并返回拒绝再次终止，未因此修改系统权限。最终仍必须核对实际版本、原加密配对、正式 WSS 身份及调试端口状态。

最终 0.3.5 已在原用户安装目录完成升级并正常启动。只读核验正式 WSS 在线、身份“小小情 / 猪猪”、原加密配对不变、图片气泡修复存在、调试端口关闭、CUA 关闭。用户电脑报告真实锁屏，未继续执行输入。临时后台安装核对脚本已结束。源码提交、安装包校验值与完整功能清单见[验收清单](desktop-pet-acceptance.md)。
